Krystal Control Panel / “Update available” — round 2

Round 2 — four systems, both states

Your cut leaves four pieces and two hard rules. Nothing below changes the card’s height in any state, and every system has an answer for online — which is exactly where #11 dead-ended.

The two rules this round is built on

  • No layout shift. A card with an update waiting must be pixel-identical in height to one without, so nothing in the grid jumps or stands out for the wrong reason. That kills #8 and every body-row idea. Both remaining mechanisms are free: a chip on the artwork sits in absolute position, and the quick row going 3→4 columns is a change within a row that already exists.
  • The marker has to survive the online state. #11’s CTA is the loudest, clearest action on the card — and it only exists when the server is stopped. So the CTA can’t be the announcement; it has to be the reward for a state marker that is present either way. That is the whole shape of the systems below: one always-on marker + one state-dependent action.
#1 → P1Version pill, head row. Quiet, informational, zero height.
#4 → P2Art chip. Loud, carries the version, free real estate.
#10 → P3Fourth quick button. Existing pattern, folds 2×2.
#11 → P4Connect-row CTA. Biggest action, offline only.
#2Split pill — pretty, impractical. Cut.
#8Inset banner — shifts layout. Cut.

The four systems

Each is a marker + action pair, drawn in both run states. Same server, same card height, every time.

P2 + P3 #4 + #10

System D — Chip + “Stop & update”

P2 + P3′ new behaviour

The only option here that changes behaviour rather than presentation. Instead of explaining that a running server can’t be updated, the button offers to do the two steps: it arms confirm-first (the pattern useConfirmAction already implements for Stop and Restart), and confirming stops the server, waits for it to land, then updates. Offline it is a plain Update — there is nothing to stop.

⚠ This needs real work behind it: a client-side sequence would break if the tab closes mid-flight, so the honest version is a backend verb that owns the stop→update→(start?) chain. Worth deciding on its own merits, not as a visual choice.

The 2×2 fold — measured, and it’s the deciding fact

You’re right that four buttons fold well. But the fold isn’t free, and it isn’t optional either — it happens at the widths the dashboard actually renders at. .server-grid is repeat(auto-fill, minmax(280px, 1fr)), and the card’s own container query stacks at max-width: 340px. Work the arithmetic against a 1280px content column:

3 columns397pxno fold
4 columns295pxfolds
5 columns233pxfolds

Four across is the ordinary desktop dashboard. It is already below the threshold — the metric row is stacked there today, which is exactly why that container query exists.

Measured: a fourth button costs 34px of card height at a real grid width

3-button card @295px301pxquick row 28px
4-button card @295px335pxquick row 62px
delta+34pxper updating card

So the 2×2 fold reintroduces exactly the layout shift you rejected #8 for — and worse, because a CSS grid row stretches to its tallest item, one updating card inflates the whole row and leaves dead space under every sibling in it. #8 at least only made its own card taller.

This is not a bug to fix. Four labelled buttons genuinely do not fit 295px on one line, and shrinking them to icon-only would cost the labels on all the lifecycle verbs to accommodate a button that is usually absent. It is the intrinsic price of System A.

System B, and the measurement makes it lopsided. It was already the only system where nothing on the card is ever disabled — an action appears exactly when it can run, and is simply absent when it can’t — and it spends the loudest slot on the card at the one moment that slot is otherwise dead weight. The chip does the announcing in both states, which is precisely the gap you spotted in #11.

What settles it is that System B is the only one that holds the no-shift rule at the width the dashboard actually renders at. Four labelled buttons cost 34px of card height at 4-up, and a grid row stretches to its tallest item, so a single updating card pads out every sibling beside it. That is the same objection that killed #8, arriving by a different route.

Pair it with the split chip — solid where it has to be legible, frosted where it carries the version — so it survives whatever cover art RAWG returns.

Two things I’d keep out of this decision. System A is the conventional runner-up and its one genuine advantage is that the update action always lives in the same place; if that matters more to you than the row inflation, it’s a defensible call, and I’d want to hear that rather than assume. System D is a behaviour change, not a visual one — it needs a backend verb that owns the stop→update chain — so it deserves its own conversation instead of riding in on a design pick.
